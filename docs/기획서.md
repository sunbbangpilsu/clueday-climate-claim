## 1. 문제와 사용자

### 가입 사실을 아는 것만으로는 청구 준비가 끝나지 않는다

경기 기후보험은 별도 가입 절차 없이 대상 도민에게 적용되지만, 피해 도민이 보험사에 직접 청구해야 합니다. 공식 안내에는 청구서·동의서와 항목별 진단·진료 증빙이 제시돼 있습니다. 청구 준비에는 자신의 진료 조건을 확인하고 필요한 서류를 구분하는 단계가 필요합니다. [1]

안양시는 2026년 9월 29~30일 서류 작성과 신청 절차에 어려움이 있는 시민을 위한 현장 지원을 운영했고, 268명 방문·225건 접수가 보도됐습니다. 이는 대면 지원 수요의 근거이며, 전체 미청구율이나 웹서비스 효과를 뜻하지 않습니다. [2]

| 사용자 | 해결하려는 상황 | 제공 가치 |
|---|---|---|
| 어르신·기후취약계층 | 보장 조건과 서류를 한 번에 파악하기 어려움 | 입력 조건별 예상 항목·확인 대기·서류 준비를 구분 |
| 보호자 | 가족의 여러 진료 건을 대신 준비해야 함 | 사람과 진료 건마다 독립된 기록 |
| 야외 활동·노동자 | 진료 상황 전달과 증빙 준비가 필요함 | 직접 입력한 상황 카드와 준비 안내 |

초기 핵심 사용자는 **보호자가 함께 준비하는 어르신·취약계층**입니다. 사용성 조사는 아직 수행 전이며 아래 계획으로 검증합니다. 지급 실적과 환자 수의 단순 차이를 미청구 인원으로 계산하지 않습니다.

## 2. 해결 방식과 1차 구현 범위

**조건 입력 → 예상 보장·확인 대기 구분 → 서류 체크 → 준비 요약서 → 공식 채널 접수**로 연결합니다. 접수와 지급 심사는 보험사가 담당합니다.

| 화면 | 현재 가능한 동작 | 화면·API 연결 |
|---|---|---|
| 홈 | 서비스 범위, 실제 특보 미확인 안내, 일반/시연 구분 | #home / GET alerts |
| 진료 카드 | 빈 양식에 입력한 환경·활동·시간·증상으로 카드 생성 | #card / POST doctor-card |
| 보장 입력 | 날짜·사고 지역·가입 조건·질병코드·감염병·상해 등 입력 | #check / POST eligibility |
| 결과 | 조건부 예상 금액, 확인 대기 항목, 근거와 서류 체크 | #result / 판정 응답 |
| 준비 요약서 | 진료 건별 작성 보조 문서, 인쇄/PDF 저장, 공식 절차 안내 | #claim / GET claim-channels |
| 가족 관리 | 가족 추가, 사람별·진료 건별 독립 입력과 기록 복원 | #family / 브라우저 저장 |

### 현재 제공하지 않는 기능

실제 기상청 특보 연동, 사진 글자 인식(OCR), 자동 푸시 알림, 기관 대시보드는 **개발 예정**입니다. 현재 일반 모드에서는 샘플 특보를 실제 자료로 사용하지 않으며, 특보가 필요한 항목을 미대상으로 확정하지 않고 확인 대기로 남깁니다.

### 가상 시연 시나리오

2026.12.16 부천시의 샘플 한파, 사고 당일 가입 대상·취약계층인 가상 어머니(72세), T68 진단, 응급실 진료, 입원 2일, 별도 통원 1회를 가정합니다.

| 계산 항목 | 시연 금액 |
|---|---|
| 한랭질환 진단비 / 응급실 내원비 | 15만 원 / 10만 원 |
| 입원 2일 / 통원 1회 | 20만 원 / 2만 원 |
| 가정한 조건의 합계 | **47만 원** |

실제 증빙·병급·기지급 여부를 검증한 지급 확정액이 아닙니다. 시연은 개인 기록을 읽거나 저장하지 않습니다. 준비 요약서는 공식 청구서·동의서·서명·증빙을 대체하지 않습니다.

## 3. 차별성과 기술적 실현 가능성

### 차별화의 초점: 혜택 설명 이후의 준비 과정

| 비교하는 접근 | 청구리의 설계 방향 | 현재 검증 상태 |
|---|---|---|
| 공식 안내 페이지·접수 채널 | 진료 조건별 항목과 준비물을 정리한 뒤 공식 접수로 연결 | 조건 입력·준비 요약서 구현 |
| 일반적인 문답·요약 | 같은 입력에 같은 규칙을 적용하고 근거·보류 이유를 표시 | 규칙 기반 API 구현 |
| 가족이 각자 메모로 관리 | 사람·진료 건별 질병·서류·계좌 기록을 분리 | 상태 분리 테스트와 화면 확인 |
| 특보 정보와 약관을 따로 확인 | 특보 확인 상태와 보장 조건을 연결 | 샘플 시연 구현, 실제 데이터 연동 예정 |

위 표는 서비스의 설계 차이를 설명합니다. 기존 서비스 전체에 대한 우위나 효과가 입증됐다는 뜻은 아니며, 최종 평가 전 동일 과제 비교 실험으로 검증할 계획입니다.

### 구현 구조

모바일 웹(HTML/CSS/JavaScript) → FastAPI 요청 → 보장표·판정 규칙 → 예상 항목 / 확인 대기 / 서류 응답.

| 정보 | 처리·보관 경계 |
|---|---|
| 이름·연락처·계좌·가족, 진료 건별 기록 | 브라우저 로컬 저장소. 사람·진료 건별 분리 |
| 판정용 날짜·시군·질병코드·조건 | 서버로 전송해 처리하되 서버 저장 안 함 |
| 진료 카드의 노출·증상 문구 | 카드 생성 API로 전송해 처리하되 서버 저장 안 함 |
| 진단서 사진 | 현재 업로드·OCR 기능 미제공. 기기 내 처리 방식은 후속 검증 |
| 샘플 특보 | 출처와 미검증 상태 명시. 실제 특보 없음의 증거로 사용 안 함 |

### 잘못된 결과를 줄이는 경계

일반 모드 미래 날짜·잘못된 코드 형식 거부, 가입 대상 미확인 시 요약서 보류, 기지급 진단비 제외, 기존 연도 지원 범위 구분, 특보 미확인 시 보류, 진료 내용 변경 시 이전 결과 무효화, 새 진료 건의 서류 체크 초기화를 구현했습니다. 질병 진단과 최종 보험금 지급 판단은 수행하지 않습니다.

## 4. 실행 계획과 검증

### 현재 확인한 결과

- 서버 회귀 테스트 **33개**, 화면 상태 테스트 **7개**, 총 **40개 통과**.
- 최소 제출 조건인 프론트 1페이지·백엔드 1엔드포인트를 넘어 화면 6개와 API 6개 제공.
- 브라우저에서 사람/진료 건 전환, 감염병 입력, 상황 카드 생성, 준비 요약서 동작 확인.
- 320px·390px 및 큰 화면에서 주요 화면 배치 확인.
- 기관 협약·이용자 인터뷰·실제 보험금 수령 성과는 아직 확보하지 않았음.

| 기간 | 필수 작업 | 완료 판단 기준 |
|---|---|---|
| ~10/26 | 1차 시제품·문서·6화면 제출 | 로컬 실행과 핵심 흐름, 테스트, 파일 확인 |
| 10/27~11/2 | 보호자·어르신 5명 인터뷰, 담당자 1~2명 협조 요청 | 이해하기 어려운 표현과 준비 단계 기록 |
| 11/3~11/9 | 실제 특보 이력 연동 검증, 실패·조회 불가 처리 | 실제/미확인/없음 구분 및 자료 출처 대조 |
| 11/10~11/16 | 사용성 비교 10명, 접근성 개선, 회귀 검증 | 준비 과제 완료율·시간·오류 기록 |
| 11/24 | 가상 사례와 보류 사례 시연 | 성공 흐름과 한계·확인 대기 설명 |

OCR·푸시·기관 대시보드는 핵심 흐름이 안정된 뒤의 선택 범위입니다. 연동이 지연되면 일반 모드의 확인 대기 원칙을 유지하고, 시연에는 가상 사례임을 표시합니다. 기관 섭외가 안 되면 보호자 중심 사용성 검증을 먼저 수행합니다.

| 역할 | 담당 |
|---|---|
| 팀장·총괄 | 명지훈 |
| 기획·사용자 조사 | 박정민 |
| 백엔드·판정·데이터 연동 | 김동건 |
| 프론트엔드·접근성 | 고건 |
| 디자인·UI/UX·마스코트 | 천세훈, 노경민, 정지인 |

### 사용성 평가 설계 (예정)

동일한 가상 사례로 공식 안내만 이용하는 조건과 청구리 이용 조건을 비교합니다. 순서 효과를 줄이도록 이용 순서를 나누고, 준비 항목 찾기와 확인 대기 이해 여부를 관찰합니다. **10명 중 8명 이상 핵심 과제 완료, 중간 소요 시간 감소**를 목표로 하며, 현재 달성 실적으로 표현하지 않습니다.

## 5. 운영·지속 가능성·성과

### 시민 무료, 작은 운영 범위에서 검증

현재는 로컬 실행으로 제공하며 유료 호스팅을 구매하지 않았습니다. 시범 운영 시에는 월 5만 원 이내를 예산 검토 상한으로 두고, 호스팅·모니터링·오류 대응 비용을 산정할 계획입니다. 이 금액은 업체 견적이나 확보된 예산이 아닌 계획 가정입니다.

장기 재원은 학교·지역사회 협력 지원과 지자체·보건소의 운영 도입을 검토합니다. 기관용 도구의 라이선스·유지보수 계약은 **미검증 수익 모델 가설**입니다. 시민 청구 수수료나 보험금 비례 수수료는 받지 않습니다. 기관 도입 없이도 핵심 무료 안내를 유지할 수 있는 범위부터 검증합니다.

| 운영 항목 | 담당·주기 | 처리 방법 |
|---|---|---|
| 보장표·접수처 변경 | 기획+백엔드, 월 1회 및 개정 시 | 공식 출처 확인, 변경 기록, 규칙 테스트 |
| 잘못된 안내·연동 오류 | 백엔드+프론트, 발견 시 | 해당 항목 보류, 원인 수정·재검증 |
| 브라우저 기록 관리 | 프론트, 버전 변경 시 | 사람/진료 건 분리, 기존 입력 보존, 이전 결과 재확인 |

| 성과 지표 | 측정 방식·한계 |
|---|---|
| 준비 과제 완료율·소요 시간 | 동의한 참여자의 가상 과제 관찰. 목표와 결과 분리 |
| 보류 결과 이해율 | 특보 미확인을 미대상으로 오해하는지 질문 |
| 가족 기록 분리 오류 | 사람·진료 건 전환 회귀 테스트와 사용성 관찰 |

| 위험 | 대응 |
|---|---|
| 특보·약관 정보 미확인 | 금액 합산을 보류하고 공식 확인 경로 제공 |
| 고령자 입력 부담 | 큰 글씨·명확한 라벨·보호자 지원, 인터뷰로 개선 |
| 기능 범위 확대 | 실제 특보 대조·준비 흐름 우선, OCR 등은 선택 범위 |
| 실제 효과 미입증 | 테스트 통과와 사용자 효과를 구분해 결과 보고 |

### 평가 기준 대응

- **기획 완성도 20%:** 문제→대상→준비 흐름→핵심 범위→검증의 연결.
- **실행력·지속 가능성 40%:** 실행되는 시제품, 40개 테스트, 일정·역할·갱신 절차와 재원 가정.
- **창의성 40%:** 혜택 설명을 넘어 사람·진료 건별 준비 과정을 연결하고, 확인되지 않은 특보를 보류 상태로 다루는 설계.
